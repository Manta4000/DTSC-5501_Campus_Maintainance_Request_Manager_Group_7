In our design the musts we have are that size cannot be negative, size cannot be greater than capacity, and must resize when the capacity has been hit.

In both requests IndexError is raised when index is out of the range or when it is missing all together. TypeError is raised when the index is not an integer and ValueError when a duplicate id has been found. 

Our Array Request will double its capacity when it needs to be resized then copy over the old data to the new bigger list. When we insert or remove it will shift the data to the correct position based on what was moved and where the gap needs to be filled. It is important that 0 <= size <= capacity is always true and request must = size not capacity. Each request must also have its own unique request_id tied to its data. In our array the time complexity for push, insert, and remove will be O(n) because we need to shift the old data depending on where the new data is going. Append can be O(1) until we need to resize then it will be O(n). Count will be O(1) as it is already stored in self.size. GetAt will be O(1) as we have the index to call to go to it. FindById will be O(n) as we will need to go through as many as needed to find out match on the id. 

Our Linked Request will have nodes, and each node will store one request. The linked request was made with only a head node and leaves out tail and cached size. This makes it simpler but changes a few time complexities. When the list is empty head will be none to avoid errors when running. Time complexity here is easy because since we made this without a tail or a cached size everything will be O(n) due to starting from the head every time and starting a count every time rather than having a stored count of nodes. If we had a tail node we could make append the time complexity O(1) and the time complexity for the count would be the same as the new append if we had stored the size rather than count each time.
